# WorkBuddy Manager 统一客户端开发——Codex 项目总任务 V1.0

## 0. 你的角色与任务

你是本项目的首席软件架构师、Rust/Tauri 开发工程师、Windows 平台工程师、测试工程师及安全审计负责人。

你的任务是在 Windows 环境中，基于两个真实 GitHub 开源项目，构建一个可独立安装、可长期维护的 WorkBuddy 多账号桌面管理器。

两个上游仓库：

主项目：
[https://github.com/changexbc/workbuddy-switch](https://github.com/changexbc/workbuddy-switch)

功能参考项目：
[https://github.com/autumnsentiment/workbuddy-helper](https://github.com/autumnsentiment/workbuddy-helper)

原则：

- 以 workbuddy-switch 为主体，尽可能保留已有、经过测试的功能。
- 从 workbuddy-helper 提取或重新实现必要的签到、调度及积分能力。
- 最终交付一个统一的 Windows 桌面程序。
- 优先采用 Tauri + Rust + TypeScript。
- 不以两个进程长期互相调用作为默认架构。
- 不为了减少代码量而牺牲数据安全、兼容性和维护性。
- 不能依据 README 推断已经实现某项功能，必须检查源码、执行测试并记录证据。
- 不得虚构测试通过、成功登录、成功签到或成功同步。
- 不得使用真实用户数据作为初始测试数据。
- 不得自行绕过验证码、设备验证、反自动化限制或服务端风控。
- 不得为了实现国际版自动活跃而伪造官方客户端身份或制造虚假的有效使用记录。

本项目不要求三个 WorkBuddy 账号同时运行。只要求多个账号可以安全地切换和管理。

## 1. 预期软件规格

产品名称：WorkBuddy Manager

目标平台：

- Windows 10/11 x64
- 优先支持当前 Windows 普通用户模式
- 不要求常驻管理员权限
- 不依赖 Docker
- 最终使用无需安装 Go、Rust、Node.js
- 开发环境允许使用上述工具链

目标功能：

1. 管理至少 3 个 WorkBuddy 账号。
2. 支持账号添加、删除、备注、状态查看、重新授权。
3. 支持国内版、国际版账号分类。
4. 一键切换当前 WorkBuddy 登录身份。
5. 切换后保留原有会话。
6. 将选定会话复制给另一账号。
7. 支持关联会话的手动增量同步。
8. 支持内容分歧检查和用户选择。
9. 支持国内版单账号签到和批量签到。
10. 支持每日北京时间自动签到。
11. 展示签到结果、积分、套餐到期时间。
12. 保留原项目已有的 Token 统计能力。
13. 提供账号、签到和会话操作日志。
14. 实现安全备份与恢复。
15. 提供 Windows 安装程序。

不开发：

- 同时运行三个 WorkBuddy 桌面进程。
- 多台电脑实时云同步。
- 绕过平台的配额、付费、验证码及安全限制。
- 自动注册账号。
- 共享或出售第三方账号。
- 未经批准的国际版虚假活跃请求。
- 未经用户确认的全量会话数据库重写。

## 5. 阶段 02——统一账号管理与凭证架构

目标：一个账号目录，多个独立的授权用途，避免重复数据和凭证写入冲突。

### 5.1 账号模型

建立或扩展以下概念：

Account：

- internal_id
- provider
- region
- external_uid
- display_name
- remark
- status
- is_enabled
- created_at
- updated_at

AccountCapability：

- account_id
- capability_type
- authorization_status
- expires_at
- last_verified_at

Capability 类型建议：

- DesktopSwitch
- Checkin
- PointsRead

CredentialReference：

- account_id
- capability_type
- secure_storage_key
- expires_at
- credential_version

不得在普通账号表中保存明文 Token。

### 5.2 凭证处理原则

1. 不假设 Switch 和 Helper 的授权令牌天然兼容。
2. 比较受众、作用域、签发方、生命周期和刷新机制。
3. 仅在确认合法且安全的情况下复用授权。
4. 如不能复用，允许同一账号对应两个独立授权能力。
5. 优先采用 Windows DPAPI 或原项目已审计的加密实现。
6. 密钥不得硬编码。
7. 不得向前端直接返回完整令牌。
8. 不能在日志或错误消息中输出凭证。
9. 不得通过复制另一个账号的认证文件来实现授权。
10. 任何迁移前先创建可恢复备份。

### 5.3 账号唯一性

账号唯一标识必须包含服务区域或服务提供方。

不要仅凭显示名、手机号尾号或本地备注判断账号是否相同。

对于同一个账号，允许拥有多个不同用途的授权能力。

### 5.4 统一账号服务

建议抽象：

AccountRepository
AccountService
CredentialStore
AuthorizationProvider
SessionService
CheckinService
PointsService

按主项目已有实现调整，避免重复建设。

验收：

- 测试账号增删改查正常。
- 相同显示名不会导致账号合并。
- 国内版/国际版不会错误混合。
- 敏感凭证无法通过 UI、日志或普通导出获得。
- 无效凭证会正确提示重新授权。

## 6. 阶段 03——签到能力迁移

目标：将 Helper 的签到相关功能整合为主项目可调用的 Rust 模块。

### 6.1 实施策略

优先阅读和理解 Go 原始实现，再编写 Rust 对应适配器。

不得直接逐行机械翻译。

应尽可能保留：

- 响应解析逻辑。
- 业务状态判断。
- 失败分类。
- 重试保护。
- 签到结果语义。

可以改进：

- 数据模型。
- 与主项目的共享状态。
- 错误类型。
- 任务调度。
- 日志结构。
- 测试覆盖。

### 6.2 签到接口

建议设计业务方法：

checkin(account_id)
checkin_all()
get_checkin_status(account_id)
get_checkin_history(account_id)
refresh_points(account_id)

其中 checkin_all 必须支持：

- 单账号失败不影响其他账号。
- 不重复提交已经成功的当日任务。
- 逐账号记录执行结果。
- 受控并发和服务端限速。
- 人工取消。
- 授权失效时停止并提示重新登录。

### 6.3 签到结果状态

至少区分：

- Success
- AlreadyCompleted
- AuthExpired
- RequiresUserAction
- RateLimited
- NetworkError
- ServerError
- Unsupported
- Unknown

如果请求超时且结果不确定，应先查询服务端状态，再决定是否重试。

“请求已发送”不等于“签到成功”。

“签到成功”也不等于“积分立即到账”。

### 6.4 外部接口风险

所有签到和积分请求应集中封装在可替换适配器中。

不能在 UI、定时任务及数据库层散布 URL、字段名称或具体鉴权细节。

不得模拟不存在的官方授权。

如果接口需要绕过安全挑战、伪造受保护客户端身份或不符合当前服务规则，该能力必须禁用并报告，不允许以绕过手段继续。

### 6.5 测试

必须编写 Mock HTTP 测试，不得依赖真实账号完成自动化测试。

覆盖：

- 成功。
- 当日已签到。
- 令牌过期。
- 超时。
- 429 限速。
- 500 服务端异常。
- 返回 JSON 不完整。
- 服务端字段变更。
- 同账号重复触发。
- 三账号部分成功。

验收：

- Mock 测试通过。
- 操作日志与业务结果一致。
- 账号切换功能不受签到模块影响。
- 不对生产接口进行压力测试。

## 7. 阶段 04——自动签到任务调度

目标：提供稳定、可配置、可审计的每日签到。

### 7.1 调度规则

- 使用 Asia/Shanghai，即北京时间。
- 默认每日执行时间 09:15。
- 用户可以修改。
- 每个账号有独立启停状态。
- 每个账号每日最多记录一次成功签到。
- 使用任务状态保证幂等。
- 避免重复调度器同时运行。
- 实际执行时间需在日志中记录。
- 支持软件启动后恢复待执行任务。

### 7.2 断电与补执行

建议规则：

软件启动后：

1. 检查当日签到状态。
2. 检查计划执行时间。
3. 如果已过计划时间且尚未完成，按用户启用的补执行策略处理。
4. 不得为了补执行而在同一天无限重复请求。
5. 不允许把前一天未签到的记录错误计入当天。

默认补执行策略：
软件启动后，当日计划任务已错过且尚未完成时，可以自动执行一次。

必须提供关闭补执行的配置。

### 7.3 Windows 启动

优先采用当前用户登录自启动或受控的 Windows 任务计划程序。

不要求系统管理员权限。

如果使用任务计划程序：

- 需要显式启用。
- 提供关闭和卸载清理功能。
- 防止与常驻调度器同时执行。
- 不得把令牌放在命令行参数里。
- 必须说明未登录、睡眠、关机状态下的实际运行限制。

### 7.4 调度测试

采用注入时钟测试：

- 计划前。
- 到达计划时间。
- 计划执行后。
- 软件关闭重启。
- 系统时间向前调整。
- 系统时间向后调整。
- 日期跨零点。
- 并发启动两个调度进程。
- 三账号不同完成状态。
- 网络断开和恢复。

验收：

- 不重复执行。
- 不误判日期。
- 自动启动与计划执行互不冲突。
- 所有失败可追踪。

## 8. 阶段 05——会话保留、复制、增量同步

本阶段以保留主项目现有功能为主，不允许为了整合签到而重构整个会话系统。

### 8.1 基本原则

- 切换账号不删除原账号会话。
- 会话复制不删除源会话。
- 目标账号创建独立会话副本。
- 关联关系持久化。
- 增量同步为用户手动触发。
- 不允许未经确认覆盖出现分歧的会话。
- 不对运行中的活跃会话执行危险写入。
- 不修改共享数据库的账号过滤规则来实现“全局可见”。

### 8.2 数据安全

写入前必须：

1. 检查 WorkBuddy 版本。
2. 检查数据库路径。
3. 检查 SQLite schema。
4. 检查数据库可写性和占用状态。
5. 检查关联的账号及会话。
6. 创建一致性备份。
7. 验证备份可以正常读取。

写入时：

- 使用事务。
- 不得直接操作不完整的 SQLite 主数据库副本。
- 正确处理 WAL。
- 检查外键及完整性约束。
- 确认主项目现有同步算法的事务边界。

写入后：

- 验证记录完整性。
- 验证源会话未损坏。
- 验证目标会话新增内容。
- 记录操作前后摘要。
- 失败时执行完整回滚或恢复备份。

### 8.3 测试场景

A. A 账号创建会话，切到 B，再切回 A，会话仍存在。

B. A 的会话复制给 B，A 原始会话内容不变。

C. B 在复制会话中新增内容，手动同步到 A。

D. A 和 B 分别新增不同内容，系统识别分歧。

E. 用户取消冲突处理，不发生任何会话覆盖。

F. A 的会话关联到 B、C，分别执行增量同步。

G. 同步过程中断电或强制结束程序，数据库可以恢复。

H. WorkBuddy 版本或 schema 发生不兼容变化时，禁止执行写入。

I. 会话包含附件或本地路径时，提示附件和文件引用不能自动保证同步。

J. 复制、增量同步和恢复均不会造成重复消息或错误归属。

不得用生产环境真实项目进行破坏性测试。

- 北京时间选择。
- 单账号启停。
- 今日执行状态。
- 立即签到。
- 批量签到。
- 失败重试。
- 上次签到记录。
- 下次预计执行时间。
- 错过计划后的补执行开关。

### 9.3 会话管理页面

保留：

- 原账号会话列表。
- 跨账号复制。
- 关联会话。
- 增量同步。
- 冲突预览。
- 用户确认。
- 操作备份。

新增签到功能不得覆盖原有会话入口。

### 9.4 错误提示

错误提示需使用明确中文：

- 登录失效，需要重新授权。
- 网络连接失败。
- 签到已完成。
- 服务端要求用户操作。
- 当前 WorkBuddy 版本未通过兼容性验证。
- 会话数据库正被占用。
- 备份失败，本次操作已取消。
- 同步出现冲突，需手动选择。

不得把任何内部错误都统一显示为“操作失败”。

## 10. 阶段 07——安全、测试和发布

### 10.1 必需的安全措施

- 凭证加密存储。
- 最小权限。
- 不明文记录 Token。
- 不上传本地会话内容。
- 不开放未认证的远程管理端口。
- 防止路径遍历。
- 防止任意文件读取。
- 防止恶意参数传递给 Tauri 命令。
- 防止并发写入认证文件。
- 防止重复签到。
- 升级前验证数据兼容性。
- 备份文件设置合理的访问权限。
- 账号删除前用户确认。
- 不允许后台静默修改正式会话数据库。

### 10.2 自动测试

至少覆盖：

- Rust 单元测试。
- 前端单元测试。
- 账号模型测试。
- 凭证存储测试。
- 签到 Mock 测试。
- 调度 Mock 测试。
- SQLite 迁移测试。
- 会话复制测试。
- 增量同步测试。
- 冲突处理测试。
- 回滚测试。
- 安装程序构建测试。

每个失败必须记录，不能仅展示成功测试数量。

### 10.3 手工集成测试

使用三个获授权的测试账号。

需要用户明确授权后，才允许进行真正的登录、签到或会话迁移测试。

测试步骤：

1. 添加账号 A、B、C。
2. 查询三账号信息。
3. A → B → C → A 切换。
4. 验证原账号会话保留。
5. A 的测试会话复制至 B。
6. B 新增测试内容。
7. 手动增量同步到 A。
8. 对冲突情形进行测试。
9. 三账号执行签到状态查询。
10. 对允许签到的账号执行一次真实签到。
11. 验证积分状态。
12. 验证定时执行。
13. 重启程序后验证持久化状态。
14. 恢复备份并验证数据。
15. 卸载和重装测试。

如果用户没有提供测试账号，必须保留真实账号验收为“未执行”，不能虚构测试结果。

### 10.4 发布要求

生成 Windows x64 安装包。

至少提供：

- 安装程序。
- 版本号。
- Git commit SHA。
- SHA256 校验值。
- LICENSE 和 THIRD_PARTY_NOTICES。
- README。
- 安装说明。
- 用户数据备份说明。
- 已知问题。
- 测试报告。
- 升级及回滚说明。

如果无法进行代码签名，应明确说明安装包未签名，不得声称已通过 Windows SmartScreen 信任验证。

禁止把所有改动压成一个无法审查的大提交。

## 12. 开发过程中的决策机制

对于普通实现细节，可以自主决策，但必须记录理由。

遇到以下情况时必须停止相关高风险操作并报告：

- 源码与 README 明显不符。
- 账号凭证格式无法安全识别。
- 需要读取或修改用户真实账号 Token。
- 需要写入生产会话数据库。
- 无法确定协议或授权边界。
- 签到接口需要绕过安全验证。
- 依赖许可证存在分发冲突。
- 备份或恢复测试失败。
- 客户端数据库 schema 不兼容。
- 无法完成测试但准备发布。

如果某个可选功能不可靠，应将其隔离或禁用，不得为了满足功能清单牺牲整个软件的稳定性。
