# WorkBuddy Manager 拓展执行方案 V1.1

日期：2026-10-15。性质：开发执行方案；本文件不代表新增能力已实现，也不自动启动任何活动动作。

本版根据用户要求，将“成长任务自动执行”列为明确交付目标。只读页面是实施步骤，不是最终产品边界；本文件替代 V1.0 的实施顺序。稳定性通过防重复、结果核实、失败隔离和实际验收保证，不承诺第三方活动永远开放或所有任务必然成功。

## 1. 结论与目标

保留 Manager 的 Rust/React 主体，按需要吸收 workbuddy2api-panel 的任务闭环、账号状态和运行观测设计。按“查询与状态 → 自动领取 → 已验证任务的自动接受/执行 → 旅行”的顺序形成完整自动化。模型目录是独立可选批次；API 网关不纳入本轮开发承诺。

本方案服务于现有 Windows 单机、多账号、客户端切换和本地会话管理场景。成功标准是用户能看到真实状态、清楚知道哪些动作已生效，并可靠处理当前账号实际具备的活动资格；不以追平 panel 的功能数量为目标。

## 3. 最小技术约束

1. **复用现有代码。** 使用当前凭证库、原子保存、操作锁、配置 API、日志页面和两种 host 包装；不另建常驻服务、插件框架或通用工作流引擎。
2. **保留签到账本。** `daily_scheduler.rs` 的任务、状态及执行器目前面向签到，不能仅加一个任务类型字段就当成通用执行器。首轮不改签到账本格式；出现首个新增写动作时，再引入小型活动操作记录，由现有后台协调入口调用。
3. **新增用途按实际需要增加。** 查询阶段才加入 `GrowthRead`，领取阶段才加入 `GrowthClaim`，真实操作阶段再核对执行用途；旅行需要的用途届时核实。复用 DPAPI，不将现有全部账号导出为明文，也不将 Checkin/PointsRead 的验证结果自动扩写为所有用途通过。不为每个任务码建立一套凭证库。
4. **保存和运行分开。** 显示配置开关、是否具备执行条件、后台协调器是否存活、最近一次实际运行与结果；后台心跳不能代替某个功能已经运行的证据。
5. **缺失值保持未知。** 服务端未给资格、期限、奖励或模型限制时，不补确定值；缓存须标明更新时间，查询失败时保留旧数据并标记过期。
6. **新增自动动作初次默认关闭，验证后可常驻自动运行。** 用户启用并保存账号、时间和任务选择后，无需每天确认。旧版开关即便为 true，也不能在升级后突然启用此前未运行的旅行/轮换/保活。旧签到计划和账号选择保持原有行为。
7. **不重复索要已有授权。** 已有账号持有人授权和虚构测试资料继续适用。新接口仍需核对固定主机、凭证适用性和实际响应；缺少事实就暂停该功能，不要求用户重复作笼统授权声明。

## 4. 实施顺序与逐批验收

### 阶段 0：运行状态与凭证更新一致性

目标：先纠正“有开关就表示正在自动运行”的误解，为新增任务提供可靠基础。

最小工作：

- 在现有设置、账号详情中显示各能力的运行状态和具体阻塞原因。账号列表只显示摘要，不另建综合健康大屏。
- 保留凭证、用途验证、积分查询、运行结果各自的状态；签到成功不清除其他用途错误，积分查询成功不把全部功能改成正常。
- 核对 `refresh.rs` 与账号库的更新路径。相同身份/作用域允许条件更新；UID、域、租户或用途适用性变化时，不继承旧用途验证。临期凭据先尝试现有受控刷新路径；刷新失败只影响对应能力，不无限重试。
- 复用现有修订检查和原子保存，避免刷新期间用旧账号快照覆盖用户设置。凭证版本/摘要只用于本机一致性检查，不显示或写入普通日志。
- 凭证替换后，在对应新增用途再次提交写动作之前先只读核验，确认身份和用途适用性；不能因刷新请求成功就直接沿用所有能力的可用状态。
- 不启动通用刷新、旅行和 CLI 轮换循环，不为了实现状态展示先重构所有模块。

主要位置：`app/crates/wb-switch-core/src/modules/manager_scheduler.rs`、`account_repository.rs`、`refresh.rs`、现有 `SettingsPage.tsx`/`AccountsPage.tsx`；两种 host 只增加必要的薄包装。

验收：

- 关闭、未启动、凭证不可用、接口未验证、最近运行失败能区分展示；没有观测记录时显示未运行/未知。
- 只保存设置不增加真实请求；旧签到时间、账号选择、当天尝试记录和既有会话关联不变。
- 模拟过期刷新、并发设置保存和身份变化，验证没有错误继承用途验证或覆盖新数据。

### 阶段 1：成长任务查询与最小界面

目标：用户可以按账号查看当前真实任务和可处理事项。

最小工作：

- 新增 `growth.rs` 查询/解析模块与一个“成长任务”页面，通过既有 Tauri/Web API 层接入。
- 参考 panel 的 `internal/upstream/tasks.go`，但以实际只读响应确认接口与字段。其文件头注释与后部领奖路径已有不一致，不能直接按注释实现写接口。
- 先支持手动刷新；逐账号处理，初始跨账号并发上限为 1。已有三账号规模没有必要直接实现动态并发池。
- 展示任务来源、服务端任务码、所属活动/周期、资格、进度、已领取状态、期限、奖励及更新时间。服务端只给进度时，“可能可领取”属于推算，不能冒充明确资格。
- 新增用途接入现有凭证库；只保存固定主机和用途的验证结果，不允许账号数据拼接任意请求地址。
- 暂不提供接受任务、执行任务、领奖和自动刷新循环。未知任务、活动过期或缺失字段均可只读显示。
- 在现有日志页增加必要的账号/任务类型/结果筛选；只记录执行 ID、时间、来源、业务状态和脱敏错误，不记录任务正文、Token、完整请求头或带凭据的 URL。不建设全新日志平台。

主要位置：新增 `app/crates/wb-switch-core/src/modules/growth.rs`、`app/src/pages/GrowthTasksPage.tsx`；按需修改 `credential_store.rs`、`account_repository.rs`、`src/lib/api.ts`、`src/lib/types.ts`、现有路由/导航、`OperationLogsPage.tsx` 和两个 host 的接口包装。

验收：

- 请求测试证明所有入口只发允许的 GET；页面、手动刷新和升级均不触发 POST。
- 覆盖正常、空列表、字段缺失、未知任务、过期活动、401/403、限流、网络失败和缓存过期。
- 真实只读核对 A/B/C 的账号身份和任务状态，和官方可见信息核对；活动未对某账号开放时如实显示“不适用”，不计失败也不计完成。
- 程序重启、升级与损坏缓存不改变签到计划、凭证、会话数据。

阶段 0 与 1 通过后可以提供中间测试版本，但不能据此宣布成长任务自动化完成。继续执行阶段 2—4；只对外明确列出已实现的范围。

### 阶段 2：普通奖励自动领取

目标：处理已有进度和既得奖励，不代用户模拟完成任务。

最小工作：

- 首次只接入一个已核实、当前仍有效的普通领奖动作。手动单项验证后，接入自动扫描与领取；手动和自动必须调用同一服务函数。自动领取是本批必做，不能以仅有按钮代替完成。不同时增加自动兑换和抽奖。
- 执行前重新查询身份、活动有效性、资格与领取状态；提交后再次查询服务端状态，区分已领取、本次领取、未到账和结果未知。HTTP 200 不作为成功依据。
- 增加小型 `activity_operations` 记录和账号互斥，复用已有 durable write/锁机制，不把活动结果塞进旧的 `CheckinResult`。
- 幂等身份使用账号身份（provider/region/UID）、活动 ID、任务码、奖励实例或服务端周期、动作类型。只有明确每日任务才按北京时间日期分段；一次性奖励不能每天重新获得一次幂等额度。刷新 Token 不改变幂等身份。
- 提交前持久化操作记录。发送后超时/崩溃，恢复时先只读核实；没有可靠核实接口时保持结果未知，不自动重发领奖。
- 取消只停止后续动作；已经发出的请求继续登记待核实。手动、批量和自动领取共用同一操作记录与活动执行锁。
- 经验证的任务领取可复用同一适配器，但必须对活动、账号资格、周期和响应状态逐项检查；任务清单里出现新任务不代表自动获得执行支持。

主要位置：扩展 `growth.rs`，按需要新增 `activity_operations.rs`，调用现有协调入口、锁与凭证模块；不在第一阶段预建通用插件系统。

验收：

- 模拟已领取、领取成功、业务拒绝、活动结束、超时但已到账、重启中断、重复点击和双 host 同时操作。
- 在真实已有可领取奖励的一个测试账号上执行一次，核对领取前后服务端状态，不伪造测试进度。若当时没有符合条件的奖励，标为真实验收待条件，不靠事件上报造出资格。
- 通过后再验证其余适用账号；无资格账号正确跳过。
- 启用自动领取后跨一个北京时间日期边界运行，重启后不重复领取；确认手动与后台同时触发也只提交一次。没有符合资格的真实样本时，不将隔离测试记为真实通过。

没有可靠的领取状态核实路径时，本批只保留官方处理入口，不发布自动领奖功能。连登档位查询可以复用只读列表；兑换/补签/抽奖不在本批范围。

### 阶段 3：已验证成长任务的自动接受与执行

目标：完成自动化闭环，而不局限于领取已经由用户完成的任务。

最小工作：

- 在 `growth.rs` 使用固定的已验证任务清单和普通函数分派：记录 task_code、活动、真实动作、进度查询方式、最大动作数、是否消耗积分/产生文件/创建持久对象。只在结构确有重复时抽取辅助函数，不设计动态插件、脚本 DSL 或规则引擎。
- 先选择一个当前仍开放、能可靠核实、可在虚构测试环境真实完成的任务，打通“扫描 → 判定资格 → 必要时接受 → 执行 → 查询进度 → 领取 → 再查询”闭环。接受任务不是完成，进度达标不是已领奖。
- panel 中的聊天次数/指定模型、Buddy、技能、专家、模板、创建自动化等代码只是候选线索。每项先区分真实操作和仅事件上报；活动结束或只靠伪造事件的任务不进入自动执行清单。
- 自动执行必须读取当前服务端剩余进度。确有可靠计数时只执行缺少的动作；进度滞后时等待核实，不能不断发送操作“刷到成功”。需要使用特定模型时明确选择该模型，不能静默换模型。
- 对会消耗积分的动作设置有限的次数上限，默认 1 次受控动作；一个任务确需多次时必须在启用时列明总次数。只有服务端可核算成本时才提供积分上限，不能用猜测实现虚假的费用控制。
- 涉及文件只使用虚构测试目录；涉及创建定时任务等持久对象时，必须能识别新建对象并明确是否保留。没有可靠的创建结果核实或停止/清理方式时先不开放该项自动执行。
- 仅显示已验证动作的自动开关，显示其实际影响。一次启用后在既定范围内自动执行，不每次弹窗；范围改变、增加消耗或改变目标目录时才要求重新选择。

每个任务独立验收：

1. 有固定接口/客户端操作依据、当前有效活动和明确资格。
2. 在一个测试账号完成真实操作，服务端进度与奖励状态可核实；不得只依据日志或 HTTP 200。
3. 故障测试覆盖动作提交超时、进度延迟、重复触发、接受成功但执行失败、执行成功但领取失败及重启恢复。
4. 其余适用测试账号正确执行，不适用账号正确跳过；一个任务失败不暂停全部账号签到。
5. 连续两次自动运行（循环任务应跨有效周期）无重复动作或错误奖励记录后，才将该任务标为已验证并开放自动开关。

交付时列明“自动完成并领奖”“只自动领取”“仅查询”“已过期/不支持”四类，不使用“全任务成功”笼统宣传。没有至少一个真实任务完成此闭环，本阶段不能标记通过；某些候选无法实现时逐项记录原因，不无限扩展逆向范围。

### 阶段 4：接通既有旅行能力

目标：复用现有 `travel.rs`，完成“已有实现待接通”的部分。

最小工作：

- 先核对状态查询和手动领取，再单独验证出发。已到达领取和新出发分别设置开关，保留用户的目的地选择。
- 在阶段 2 的操作记录与恢复规则成立后，才接入现有 `manager_scheduler` 协调入口；不调用遗留旅行常驻循环与新协调器同时执行。
- 自动功能只在新开关明确启用后运行；旧配置不自动视为启用授权。
- 当前主要凭证是固定用途验证凭据，旅行需要重新确认其接口适用性；不能直接解除旧的全局 `api_capability_error` 来使所有遗留接口同时开放。

验收：无旅行、旅行中、已到达、已领取、次数耗尽、活动关闭、凭证过期和未知响应均有准确状态；双 host 不重复出发/领奖；提交结果不明先核实；真实至少完成一次适用动作与重启后的状态核对。

真实旅行周期或活动资格尚未满足时，可发布前面已完成的批次，旅行继续默认关闭并显示原因。

### 可选阶段 5：模型能力目录

价值：帮助选择模型及推理档位。它不直接改善已完成的账号切换与会话迁移，因此作为独立查询批次，不阻塞成长任务与旅行批次。

- 优先在现有模型/限额入口扩展；只有现有布局无法容纳时再加页面。
- 展示模型名、区域、推理档位、平台公布的倍率/限制、数据来源、抓取时间。公开目录可展示，不表示该账号已实测可调用。
- 不为“验证可用”自动发起收费对话。公开标称上下文与账号实际平台限额分开；未知值不使用推测默认值填满。
- 复用本地缓存，不引入额外数据库、后台服务或 models.dev 强依赖。
- 用公开/虚构响应验证缓存回退、来源、缺失值与区域差异；需要账号查询时再增加实际所需用途。

## 5. 自动化稳定执行规则

### 5.1 调度与最小配置

- 两种 host 继续只有现有后台协调入口。由该入口按到期时间触发至多一个成长任务批次，批次内部顺序执行账号与动作；不启动 panel 或第二套旅行/保活常驻循环。
- 成长任务的网络等待不能阻塞原有签到心跳。可以从协调入口启动一个受控、可取消的批次任务，使用运行标志和文件锁保证最多一批；不建立消息队列服务或独立进程。
- 手动、自动及两个 host 共享一个活动执行文件锁，拿不到锁就返回“正在处理”，不排出第二份重复任务。现阶段三个账号全部串行，不实现动态并发池。
- 签到继续由原调度器处理；任务清单中的签到事项只引用原状态/入口，不由成长模块重复签到。不同动作不长期持有账号库的短期写锁，避免影响切换和凭证更新。
- 新配置只需：自动执行总开关、账号选择、每日执行时间、允许的任务清单、自动领取开关，以及旅行领取/出发选项。消耗型任务补充确有必要的有限次数或目录选择，不添加几十个高级设置。
- 新功能初次关闭。用户启用后，程序运行、电脑唤醒且网络可用时自动处理；不要求每天确认，也不新建 Windows 服务或计划任务。电脑休眠期间不保证执行，恢复后检查当前周期并补跑一次，不逐日补跑历史活动。
- 到点扫描一次；后续仅对“待核实、已知下次到达时间”等任务安排复查。15 秒心跳只是检查是否到期，不代表每 15 秒请求所有活动接口。
- 原有签到配置不作为成长自动化总开关：签到关闭时，用户仍可单独开启成长任务；成长模块故障不关闭签到。

### 5.2 持久记录、防重复与恢复

新增数据只在实际需要时保存为三个带版本的小文件：成长配置、只读缓存、活动操作记录。沿用现有原子写入和文件锁，不新增数据库。旧签到账本格式保持不变。

每次动作记录必要的账号身份、活动/任务/周期、动作类型、操作 ID、次数、状态、下一次核实时间和脱敏结果；不保存凭据和真实对话正文。状态至少能够区分尚未提交、可能已提交待核实、已核实完成、暂停处理。

执行顺序：

`拿锁 → 重查身份/资格 → 持久登记 → 提交一次动作 → 查询业务状态 → 记录已核实结果 → 释放锁`

- 重启后先恢复未核实记录，再考虑新动作。不能因为缓存丢失、Token 更新、账号重新导入或日期变化而重置同一个一次性奖励的防重身份。
- 每个真实步骤独立登记：接受、执行、领奖不能共用一个模糊“成功”标志。只领取失败时重查领取状态，不重做已完成的任务。
- 有服务端幂等键时复用同一键；没有时不承诺网络条件下严格一次提交。请求可能送达而结果未知，就停止重发并核实；查不清时只暂停这一账号的这一动作，不能报成功。
- 官方进度更新延迟时按既定复查间隔等待，不重复触发真实操作。没有明确“未执行”证据，不重放创建任务、聊天、领奖或旅行出发。
- 取消/退出停止后续动作；已发请求记为待核实。未核实记录不自动清理；恢复不依赖内存队列。
- 日志可按现有策略限制展示数量，但关键防重和未核实操作记录不按普通日志保留期删除。

### 5.3 超时与故障处理

| 情形 | 最小处理规则 |
| --- | --- |
| 只读请求网络失败/5xx | 有限重试，按下一次到期时间复查，不能在同一循环无限请求 |
| 429 | 遵守服务端 Retry-After；未给出时使用有限退避，不换指纹绕过 |
| 401 | 对适用凭据最多走一次既有刷新流程，重新核对用途；仍失败暂停该账号相应用途 |
| 403/验证码/风控要求人工操作 | 停止该动作的自动提交，记录具体状态，不换号替同一个任务反复尝试 |
| 404、未知字段或状态 | 标记接口/任务暂不可用，保留旧缓存但显示过期，不退化为伪成功 |
| 活动过期、任务锁定、不具备资格 | 正常跳过；按服务端周期或解锁时间决定以后是否再查，不标任务完成 |
| 写请求超时/连接断开/进程中断 | 进入待核实，禁止直接重复提交；先查接受/进度/奖励/旅行状态 |
| 配置或操作记录损坏 | 暂停新增活动写入，保留原文件，显示原因；旧签到及会话功能不随之停用 |

初始重试预算建议为每次扫描的只读失败至多重试 2 次，延后安排而不阻塞线程；最终间隔遵循接口实际限流条件。每个动作在接入时明确提交、核实和重试规则，不设计全局“所有失败都再试一次”。

## 6. API 网关的另案触发条件

只有用户明确需要让外部工具通过本项目调用模型时，才进入网关立项；“panel 有此能力”本身不是立项理由。立项前确认客户端、所需协议、是否使用工具调用、并发与长上下文需求。

届时比较 Rust 原生和固定版本 Go 侧车的实际维护成本，不预先承诺二选一。最小范围为 loopback、独立调用密钥、模型列表与经目标客户端验证的对话接口；管理会话与调用权限分离，来源检查保留。SSE、工具调用、请求级账号租约、限流恢复与会话粘性要作为真实开发工作评估。

不得承诺 Chat Completions 接口就能兼容所有客户端；若目标客户端需要 Responses，应按其真实协议另行核对。网关粘性不解决 WorkBuddy 云任务迁移，不得并入会话迁移验收。

不直接使用目标项目的明文 auths、默认示例 key、面向所有网卡的监听配置、Redis 镜像或隐式提示词/响应改写。已有调度和桌面主进程不得因可选网关退出而失效。

- 对改动运行有意义的核心单元/集成测试、前端相关测试、两种 host 编译与生产构建。761 核心/8 安全测试是 alpha.5 历史结果，不直接填作未来版本通过数量。
- 每批核对凭证锁定/过期、缓存损坏、身份/区域错误、超时和重启；新增写动作必须有持久幂等、未知结果核实和并发测试。无需为每个纯展示文案另造测试。
- 发布前备份 Manager 配置和状态，使用虚构数据验证升级；保留旧配置和签到账本。新增配置独立、带版本、默认关闭；不往 `deny_unknown_fields` 的旧格式强塞字段。新数据格式必须明确读取与拒绝行为。

### 必须完成的稳定性验收矩阵

| 场景 | 合格结果 |
| --- | --- |
| 旧版升级，新增自动化未启用 | 新增写请求为 0；原签到计划和当天记录不变 |
| 自动/手动/两个 host 同时处理同一任务 | 活动执行锁保证不重复执行，另一入口显示正在运行 |
| 接受后崩溃、执行后崩溃、领奖后崩溃 | 重启分别核实对应阶段，不整链重做 |
| 提交成功但响应丢失、业务进度滞后 | 保持待核实，不重复产生消耗或领取 |
| 午夜、睡眠恢复、系统时间回拨 | 按活动真实周期去重；只处理当前有效周期，不补做已失效历史任务 |
| 凭据刷新与设置保存同时发生 | 身份一致，设置不丢失，旧用途验证不错误继承 |
| 一个账号/任务失败 | 其余适用任务可继续，签到和会话迁移不受影响 |
| 新任务码、活动下线、接口结构变化 | 查询可显示未知；自动执行不启用新代码、不发送猜测请求 |
| 自动动作被取消或程序退出 | 后续步骤停止，已提交步骤有可恢复记录 |
| 清理日志或升级后再次扫描 | 关键防重记录仍有效，同一奖励不因日志清理重复提交 |

真实验收必须记录账号是否适用、活动周期、动作次数、服务端前后状态、是否有副作用以及恢复结果。数据来源和测试结论可供复查，公开记录不含 Token、密码或真实会话正文。
